# P4 becomes multi-trial — a scoring-semantics change

**Date:** 2026-09-11 15:18
**Authorises:** the owner, in response to §6 of
`20260911-1359-p4-live-confirmation.md` ("P4 is single-trial … scoring-semantics
change — owner decision").
**Status:** enacted; fast suite green (`788 passed, 12 deselected`, 435 s);
47/47 guard mutations red (4 new).

## 1. Why

P4 asks the one question the assessment turned on — does the model submit *on its
own*? — and it was sampled **once**, for 20 of the quick battery's 50 points. The
live confirmation showed what that costs: `Qwen3.5-2B-Instruct` scored 46.7
(NOT SUITABLE) and then 86.7 (SUITABLE) minutes apart, same prompt, same server,
differing only in P4. One sample of a flaky behaviour was deciding a verdict
band.

P1 already sampled three times. P4 now does the same.

## 2. The new semantics

**Three trials, three different questions** (`P4_QUERIES`). Different questions
rather than the same one three times, because the property under test is "this
model submits voluntarily", not "this model got this prompt right once"; and
trial 1 is the original single-shot query, so earlier recorded runs stay
comparable at the trial level.

| Trial outcome | Credit |
|---|---|
| Submitted voluntarily (`answer['ready'] = True` executed, no forced finalization) | 1.0 |
| Submitted only after the loop forced finalization | 8/15 — the fraction the single-shot probe gave it |
| No submission | 0.0 |

`score = 15 × mean(credit)`, so all three voluntary is 15/15, two of three is
10/15, one of three is 5/15, none is 0. `passed` requires a **majority** of
trials to submit voluntarily: a model that submits in two of three runs *is* a
voluntary submitter with a flaky habit, and the score now shows how flaky instead
of hiding it behind whichever sample was taken.

The per-trial outcomes are in the evidence, and in the result as `trials`,
`trial_results`, `voluntary_trials` and `diagnostics` (one diagnostic per
contradictory trial, in trial order — a model can fail P4 for different reasons in
different trials, and collapsing them to the first would hide the interesting
one). `diagnostic` remains the first of them, so the sweep tooling and the
recorded evidence format are unchanged; `scripts/assess_router_models.py` now
also records `p4_trial_results` per model.

## 3. The cost, and the knob

P4 is the second-most expensive probe after P1, and the wall time is now paid
three times. On a host serving a 4B model at single-digit tokens per second that
is not a rounding error, so `RLM_CHECK_P4_TRIALS` accepts 1–3:

```bash
RLM_CHECK_P4_TRIALS=1 rlm check <model> --quick     # one sample: faster, less stable
```

**Any unusable value falls back to 3, not to 1** (`0`, `7`, `abc` → 3): the knob
exists to trade stability for time deliberately, so a typo must not do it
silently. A run that used fewer than three trials says so in its own evidence:

```
NOTE: only 1 of 3 trials ran (RLM_CHECK_P4_TRIALS=1); this sample is smaller than
the default, so a verdict drawn from it is correspondingly less stable.
```

The fast test suite reflects the same cost: 257 s → 435 s, because every stub-driven
P4 test now exercises the real three-trial path.

## 4. What the change does to a verdict

The score now reports the *rate*, not one sample, so a flaky model can move in
either direction relative to its single-shot number. On the quick battery, with
P1 full and P6 at 10/15 (the recorded `Qwen3.5-2B-Instruct` profile):

| Voluntary trials (of 3) | P4 | Score | Verdict |
|---|---|---|---|
| 3 | 15/15 | 86.7 | SUITABLE |
| 2 | 10/15 | 80.0 | SUITABLE |
| 1 | 5/15 | 73.3 | MARGINAL |
| 0 | 0/15 | 46.7 | NOT SUITABLE |

The recorded single-shot runs put this model at both 46.7 and 86.7. Under
multi-trial sampling the same flakiness lands *between* them — which is the
honest answer, rather than whichever end one sample happened to hit.

**Measured the next day:** that model's three-trial battery returned the bottom
row of this table — 0/3 voluntary, P4 0.0/15, 46.7, NOT SUITABLE — with each trial
failing a different way (`20260912-0219-p4-multi-trial-live-confirmation.md`). So
the table is a mapping, not a prediction: this model is not "somewhere between",
it is a non-submitter on a cold router.

## 5. Residual: the forced-submission credit cannot fire

`has_final_answer and forced` is unreachable in the current loop: the end entry is
logged with `forced=True` only when `final_answer` was still `None`, and any REPL
submission sets it and breaks the turn loop. So live P4 outcomes are voluntary or
nothing, and the 8/15 credit is kept for continuity in case the loop changes
rather than because it fires.

That is now pinned instead of assumed:
`tests/test_model_check.py::TestP4ForcedSubmissionIsUnreachable` runs a real
submitting trajectory and asserts the end entry reports `forced=False` while a
REPL submission exists. If the loop ever makes a forced submission possible, that
test goes red and the credit becomes live rather than theoretical.

## 6. Guards and evidence

New tests: `TestProbeP4::test_runs_three_trials_by_default`,
`::test_a_model_that_never_mentions_the_line_says_so_per_trial`,
`::test_fewer_trials_is_announced_in_the_evidence`,
`TestP4TrialScoring` (a 10-case scale table plus the majority rule and a range
check), `TestP4TrialCount` (11 resolution cases plus the fail-safe direction),
`TestP4ForcedSubmissionIsUnreachable`, and
`TestP4SubmissionDiagnostics::test_every_contradictory_trial_gets_its_own_diagnostic`.

Four new mutations, all red as required (47 total):

| Mutation | Guard it proves |
|---|---|
| `R29 P4 collapses back to a single trial` | The sampling itself, and the per-trial diagnostics. |
| `R29 one voluntary trial is enough to pass P4` | The majority rule. |
| `R29 the documented partial credit for a forced submission is dropped` | The published scale. |
| `R29 an unusable trial count silently samples less` | The fail-safe direction of the knob. |
