## 1. Naming convention (from 2026-09-12)

Every document created under `docs/` from 2026-09-12 onward is named
`YYYYMMDD-HHmm-<topic>.md`, where the prefix is the document's **creation** date
and time.

- A document is **never renamed** when its content changes. The prefix answers
  "when did this come into being", not "when was it last touched".
- **Point-in-time records are never rewritten.** A correction is a new dated
  document that cites the old one and says which reading it replaces — the rule
  this corpus has followed since 2026-07, now made explicit.
- **Repo-root files are outside the rule** (`README.md`, `AGENTS.md`): they are
  entry points, not dated records.
- **Grandfathered, un-prefixed documents**: `docs/operator-guide.md`,
  `docs/rlm-local-manual.md`, `docs/rlm-kernel-manual.md`,
  `docs/extensibility-guide.md`, `docs/load-test-report.md`,
  `docs/conformance/README.md`, `docs/k4-first-run-report.md`. They predate the
  convention, and renaming them would rewrite links across ~42 documents for no
  informational gain. The list is explicit in `scripts/check_docs.py`
  (`LEGACY_UNPREFIXED`), not implied.
- **Enforced mechanically**: `scripts/check_docs.py` reports any un-prefixed
  document under `docs/` that is not grandfathered, and lints dated documents
  from 2026-09-12 onward (older records are history and stay exempt). The
  linter's own falsifiability is reproducible with
  `scripts/check_docs.py --self-test`, which plants one instance of each of the
  five defect classes and a clean negative control.

## 7. Corpus phase — "talk to the backup, generate a linked wiki"

**Opened 2026-09-12 by the owner.** The goal: point the harness at a large
read-only personal backup (unorganised text, HTML, source, PDF, archives, music,
video) so the RLM can answer questions against it and grow a linked wiki from it,
with the harness improving itself through RLM/GEPA while it does.

This is OD4's spec (`20260723-1324-rlm-memory-wiki-service-spec.md`) reached from
the harness side rather than built whole: that spec already defines the vault, a
content-addressed store, providers ("mounts") over heterogeneous sources, the
resumable per-item ingestion state machine, bounded LLM enrichment, hybrid
retrieval and the `rlm_local` helper contract (`memory.search`, `wiki.get`, …).
§7 stages it so that something is useful long before the service exists.

### The owner's hard constraint: strictly read-only over the corpus

Recorded as a non-negotiable rule in `AGENTS.md` §1.8, with the three enforcement
layers and the proof obligations. The short version: **the boundary is the mount,
not our code**, because model-authored REPL cells run as the harness user and the
`open` jail was retired as unenforceable (DG2). Everything derived from the corpus
(index, CAS, vault, checkpoints) lives outside it, and a startup assertion refuses
to run if the derived root is inside the corpus root.

### Sequencing, and why this order

1. **RO1 first, because scope is unknown.** The type mix decides everything
   downstream — how much is text at all, how much is inside archives, and how much
   is media that only has metadata worth having. An inventory is read-only by
   construction and costs no model time.
2. **RO2 before RO3.** Indexing a tree we cannot yet prove we never write to would
   be exactly the mistake the constraint exists to prevent.
3. **RO3 before RO4/RO6/RO7.** Retrieval without generation is the cheap half and
   makes the corpus *usable* immediately (search + read), whereas generation is
   the expensive half and needs budget discipline.
4. **RO5 as soon as RO3 lands** — it converts "the index should scale" into a
   measured envelope on real data, and it is the gate the project already defined.
5. **RO8 last, because self-improvement needs something to improve against**:
   eval suites derived from the corpus, not synthetic ones.

### Decided

- **Where the corpus is**: an external LUKS-encrypted drive on `lunacode`, exposed
  read-only at `/srv/corpus` (the `backup/` subtree only). Confirmed 2026-09-12.
- **Where derived state lives** (owner, 2026-09-12): **outside the corpus, on a
  separate root** — for now on the internal disk; if more privacy is wanted later
  it moves to another LUKS drive or partition. Two consequences recorded so they
  are not rediscovered: it cannot live on the external drive while that drive is
  mounted read-only, and it must not be a second mapping of the *same* LUKS
  container (Linux shares one superblock per filesystem, which is exactly the
  non-read-only hazard the mount exists to avoid). The vault root is a single
  path setting, so the later move is a path change rather than a migration.
- **The read-only guarantee is the mount** (`AGENTS.md` §1.8): `cryptsetup open
  --readonly` → sysfs `ro=1` → `ro` mount on both paths → corpus not writable by
  the harness user. Application code is defence in depth, never the boundary.
- **The harness runs beside the corpus** (owner, 2026-09-12): `~/Misc/rlm_for_local`
  on `lunacode`, venv on Python 3.14, derived state at `~/rlm-derived` (0700,
  outside the corpus). The model router is on the same host, so a corpus excerpt
  reaches only `127.0.0.1:9010` and never leaves the machine holding the corpus
  (`AGENTS.md` §1.9). The checkout is kept in sync from the repository rather than
  edited in place.
- **The corpus is reached only through the harness** (owner, 2026-09-12): ad-hoc
  shell work over the tree stops. Reads happen through `rlm_kernel/mounts.py`
  (via `rlm corpus …` or a `corpus_*` helper in a cell), and the index is built by
  the harness rather than by a hand-run walk. The one exception is the mount
  state itself (`findmnt`, sysfs), which is not corpus content.
- **The first index covers names, not contents** (owner, 2026-09-12): paths,
  sizes, mtimes and kinds for everything, no file reads, no LLM. Text extraction
  comes after RO1's scope call.
- **Index windows chain until the text index is complete, then stop** (owner,
  2026-09-15). The owner's machine, so the policy is theirs: a supervisor on
  `lunacode` (`~/rlm-derived/mine-index-chain.sh`) starts a fresh 12-hour
  `index_text` window whenever the previous one ends, stops when the queue has no
  pending items, and stops **for good** the moment the pause file exists
  (`~/rlm-derived/PAUSE-INDEX`) — a supervisor that restarts itself behind the
  owner's back would be the opposite of handing the machine over. It decides
  liveness from the heartbeat lock's age, never by probing a process (`AGENTS.md`
  §3). The remaining ~1.58M text files are ~7.5 hours of windows at the measured
  ~60 items/s.
